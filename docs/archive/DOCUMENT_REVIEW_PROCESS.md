## 审查流程概述

### 为什么需要文档审查？

- ✅ 确保文档准确性和完整性
- ✅ 保持文档风格一致性
- ✅ 提高文档可读性和可维护性
- ✅ 减少用户困惑和支持成本
- ✅ 促进知识共享和团队协作

### 审查范围

**需要审查的文档变更**:
- 新增文档
- 重大更新（>30%内容变更）
- 重构或重写
- 删除文档

**不需要审查的文档变更**:
- 修正拼写错误
- 更新版本号
- 小范围补充说明（<5行）

---

## 审查角色和职责

### 1. 文档作者 (Author)

**职责**:
- 按照文档规范编写文档
- 进行自我审查
- 回应审查意见
- 完成最终修改

**审查前自查**:
- [ ] 文档结构符合标准
- [ ] 所有链接有效
- [ ] 代码示例可运行
- [ ] 与当前版本同步
- [ ] 无拼写和语法错误

### 2. 文档审查者 (Reviewer)

**职责**:
- 审查文档质量和准确性
- 提供建设性反馈
- 确认文档符合规范
- 批准或要求修改

**审查要求**:
- 至少1名审查者
- 审查者应具备相关领域知识
- 审查时限：2个工作日内

### 3. 文档维护者 (Maintainer)

**职责**:
- 监督文档审查流程
- 解决争议和冲突
- 最终批准合并
- 维护文档质量标准

## 文档审查检查清单

### A. 内容质量 (Content Quality)

#### A1. 准确性
- [ ] 所有技术信息准确无误
- [ ] 代码示例与当前API一致
- [ ] 配置参数与实际实现匹配
- [ ] 截图和图表反映最新UI
- [ ] 数据和时间戳是最新的

#### A2. 完整性
- [ ] 覆盖所有重要功能和场景
- [ ] 包含必要的示例和用例
- [ ] 提供常见问题解答
- [ ] 包含相关文档链接
- [ ] 有明确的适用版本说明

#### A3. 一致性
- [ ] 术语使用一致
- [ ] 命名规范一致
- [ ] 代码风格一致
- [ ] 格式和排版一致
- [ ] 与其他文档无冲突

### B. 结构和组织 (Structure & Organization)

#### B1. 文档结构
- [ ] 包含标题和版本信息
- [ ] 有清晰的概述部分
- [ ] 目录结构合理
- [ ] 章节划分清晰
- [ ] 有总结和下一步指引

#### B2. 导航和链接
- [ ] 所有内部链接有效
- [ ] 所有外部链接有效
- [ ] 交叉引用正确
- [ ] 锚点链接有效
- [ ] 相对路径使用正确

#### B3. 可读性
- [ ] 语言简洁明了
- [ ] 段落长度适中
- [ ] 使用标题和列表
- [ ] 重要信息突出显示
- [ ] 技术术语有解释

### C. 技术规范 (Technical Standards)

#### C1. Markdown规范
- [ ] 使用标准Markdown语法
- [ ] 代码块指定语言类型
- [ ] 表格格式正确对齐
- [ ] 图片有alt文本
- [ ] 列表缩进正确

#### C2. 代码示例
- [ ] 代码示例完整可运行
- [ ] 包含必要的导入语句
- [ ] 有清晰的注释
- [ ] 遵循项目代码规范
- [ ] 包含预期输出

#### C3. 版本管理
- [ ] 文档版本与代码版本匹配
- [ ] 变更记录清晰
- [ ] 兼容性说明完整
- [ ] 弃用警告明确
- [ ] 迁移指南提供

### D. 维护性 (Maintainability)

#### D1. 更新便利性
- [ ] 模块化结构，易于局部更新
- [ ] 避免重复内容
- [ ] 使用引用和链接代替复制
- [ ] 有明确的维护责任人
- [ ] 更新频率建议合理

#### D2. 查找便利性
- [ ] 包含关键词
- [ ] 有索引或搜索提示
- [ ] 交叉引用完善
- [ ] 分类和标签正确
- [ ] 已更新DOCUMENT_INDEX.md

## 审查流程详解

### 流程1: 新增文档审查

```mermaid
graph TD
    A[作者创建文档] --> B[自我审查]
    B --> C{自查通过?}
    C -->|否| B
    C -->|是| D[提交PR]
    D --> E[分配审查者]
    E --> F[审查者审查]
    F --> G{审查通过?}
    G -->|需要修改| H[作者修改]
    H --> F
    G -->|通过| I[维护者最终批准]
    I --> J[更新索引]
    J --> K[合并到主分支]
```yaml

**详细步骤**:

1. **作者创建文档** (1-3天)
   - 确定文档类型和位置
   - 按照模板编写
   - 包含完整的示例

2. **自我审查** (0.5天)
   - 使用检查清单自查
   - 修正发现的问题
   - 确认文档质量

3. **提交PR** (即时)
   - PR标题: `docs: 新增[文档类型] - [文档主题]`
   - 描述文档目的和内容
   - 标记需要审查的重点

4. **分配审查者** (即时)
   - 自动分配或手动指定
   - 审查者应具备相关领域知识
   - 通知审查者

5. **审查者审查** (1-2天)
   - 使用检查清单逐项审查
   - 在PR中评论问题
   - 提供修改建议

6. **作者修改** (0.5-1天)
   - 回应所有审查意见
   - 完成修改
   - 通知审查者重新审查

7. **最终批准** (0.5天)
   - 维护者确认所有问题解决
   - 检查DOCUMENT_INDEX.md更新
   - 批准合并

8. **合并** (即时)
   - 合并到主分支
   - 添加标签
   - 关闭PR

### 流程2: 文档更新审查

```mermaid
graph TD
    A[识别更新需求] --> B{更新规模?}
    B -->|小更新| C[直接提交PR]
    B -->|大更新| D[创建Issue讨论]
    C --> E[快速审查]
    D --> F[制定更新计划]
    F --> G[执行更新]
    G --> H[完整审查流程]
    E --> I{通过?}
    H --> I
    I -->|是| J[合并]
    I -->|否| K[修改后重新审查]
```python

**小更新** (<30%内容变更):
- 修正错误
- 补充说明
- 更新示例
- 快速审查流程（1人审查，1天内完成）

**大更新** (≥30%内容变更):
- 重构结构
- 重写内容
- 添加新章节
- 完整审查流程（1-2人审查，2-3天内完成）

### 流程3: 文档删除审查

```mermaid
graph TD
    A[识别删除需求] --> B[评估影响]
    B --> C{文档是否真的冗余?}
    C -->|否| D[保留文档]
    C -->|是| E[创建删除提案]
    E --> F[团队讨论]
    F --> G{共识通过?}
    G -->|否| D
    G -->|是| H[移至archive]
    H --> I[更新索引]
    I --> J[合并删除]
```python

**删除原则**:
- 优先归档而非删除
- 保留历史记录
- 确保无外部链接依赖
- 团队达成共识

## 常见问题处理

### Q1: 审查意见不一致怎么办？

**解决方案**:
1. 讨论各自观点
2. 参考文档规范
3. 咨询维护者
4. 以用户利益为重
5. 记录决策原因

### Q2: 审查者迟迟不审查怎么办？

**解决方案**:
1. 发送提醒通知
2. 48小时后重新分配
3. 寻找其他审查者
4. 维护者直接审查
5. 记录审查延迟原因

### Q3: 文档存在严重错误怎么办？

**解决方案**:
1. 立即标记为"需要修正"
2. 通知文档作者
3. 优先处理修复PR
4. 必要时临时下架
5. 修复后重新审查

### Q4: 如何处理争议？

**解决方案**:
1. 收集各方观点
2. 参考项目规范
3. 进行团队投票
4. 维护者最终决定
5. 记录决策和原因

### Q5: 文档审查太慢影响进度怎么办？

**解决方案**:
1. 提前规划文档工作
2. 建立审查者池
3. 设置审查SLA（2天）
4. 紧急情况下维护者直接审查
5. 定期回顾优化流程

## 工具支持

### 自动化检查工具

#### 1. 文档质量检查器

```bash
# 检查文档质量
python tools/check_document_quality.py

# 输出示例:
# ✅ architecture.md - 质量评分: 9.5/10
# ⚠️  api-reference.md - 质量评分: 7.2/10 (3个断裂链接)
# ❌  new-doc.md - 质量评分: 5.0/10 (缺少版本信息)
```python

**检查项目**:
- 文档结构完整性
- 版本信息存在性
- 链接有效性
- 代码示例格式
- Markdown语法正确性

## 2. 断裂链接检查器

```bash
# 检查所有文档中的链接
python tools/check_broken_links.py

# 输出示例:
# 🔍 扫描 32 个文档...
# ✅ 找到 458 个链接
# ⚠️  发现 3 个断裂链接:
#    - docs/guide.md:45 - links to missing-file.md
#    - docs/api.md:120 - external link 404
#    - docs/faq.md:78 - anchor not found

- [ ] 代码示例可运行

- [ ] 需要文档审查
- [ ] 审查者: @username
- [ ] 重点关注: [列出需要特别关注的部分]
```markdown

### CI/CD集成

在GitHub Actions中添加文档检查：

```yaml
name: Document Quality Check

on:
  pull_request:
    paths:
      - 'docs/**'
      - '*.md'

jobs:
  check-docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Check Document Quality
        run: python tools/check_document_quality.py
      
      - name: Check Broken Links
        run: python tools/check_broken_links.py
      
      - name: Generate Stats
        run: python tools/generate_doc_stats.py
```

## 审查指标和KPI

### 质量指标

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 文档平均质量评分 | ≥ 8.5/10 | 质量检查工具 |

| 首次审查通过率 | ≥ 70% | PR统计 |

### 流程指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 审查覆盖率 | 100% | 所有文档变更都经过审查 |

| 文档更新频率 | 每月≥1次 | 保持文档时效性 |
| 用户满意度 | ≥ 4.5/5 | 用户调查 |
